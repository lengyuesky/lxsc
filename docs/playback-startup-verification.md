# 播放启动等待优化验收

2026-10-09。本文只记录本机合成音源与隔离服务的验证，不包含线上诊断数据。

## 实现

- HEAD 与 302 播放共用音频响应头校验。按歌曲、请求音质、解析版本缓存成功的媒体头 15 秒，最多 2000 条，读取不续期；失败、超时、取消及明确的非音频内容不缓存。关闭直链缓存时也关闭校验结果缓存。
- 校验缓存只保存媒体头，不保存正文、请求对象、Cookie 或签名地址；每次返回独立的头部副本。直链明确失败时同时清除该版本的成功校验，迟到结果不能重新保存；刷新、配置失效与不同音质继续隔离，新版本不能使用旧版本的校验结果。`music.urlCheckCache` 提供命中、未命中、合并、条目及在途数量。
- 高优先级音源先开始取链，1.5 秒仍未完成时启动一个备用，同时最多两个。先成功者进入既有媒体校验；成功或客户端取消后，取消并等待其余取链任务退出。备用失败不放弃仍在途的首选源，繁忙时不继续扩大发起数量；单源和定向刷新不增加并行调度。
- 缓存直链遇到 403/404/410 仍优先刷新原源。新解析的直链立即被拒绝时，先试其他候选，全部不可用才补做原源刷新，保留恢复机会。每次播放仍最多三个候选、六次媒体尝试、45 秒准备预算。
- HEAD 收到有效的 206 与完整 Content-Range 时，补齐缺失的 `Accept-Ranges: bytes`。未知或非法完整长度不据此声明范围能力。代理 GET 仍重新请求实际音频，保留客户端 Range/If-Range。

## 同条件对比

基线为 `1fd092c2ad2dc67abfdb0ac42e72446ae1453e7b`，新旧版本使用同一基准文件。Darwin/arm64、Apple M6、Go 1.27.1，每个版本一轮，初始化不计时。

| 场景 | 原逻辑 | 新逻辑 |
|---|---:|---:|
| 三个候选、首选一直不返回、第二个立即成功，45 秒总预算 | 取链 11.252 秒 | 取链 1.503 秒 |
| 同版本成功 HEAD 后立即 GET | 2 次上游预检 | 1 次上游预检 |
| 新链接连续 403、备用正常 | A → 刷新 A → B，3 次媒体请求 | A → B，2 次媒体请求 |

第一项只测量取链等待，不能推算真实手机的首播提升比例。其他项目以自动测试中的请求次数验证，不设依赖机器速度的性能门槛。

## 验证结果

- 全项目 Go 竞态测试、vet 与 65 项 Node 测试通过。
- 64 项 Chromium 验收通过，覆盖网页真实播放、直连/代理、Range、会话失效、队列、移动端布局及现有其他功能。
- 无 CGO 构建与 `git diff --check` 通过。
- 专项回归包括：快速首选不请求备用、慢源 HTTP 取消、备用失败后首选继续成功、最多两个并行源、全部取消；预检共享、绝对过期、头部副本与凭据隔离、不同音质/版本、关闭缓存、代理实际失败后刷新；新链失败优先备用、备用解析/媒体都失败时补做原源刷新、全部明确失败与网络不确定的区分。
- 浏览器使用仓库固定的 Playwright 1.58.2 和本机已有 Chromium headless shell 1243，通过 `LXSC_CHROMIUM_PATH` 指定。未新增或更新第三方依赖。

## 行为与上线边界

音源优先级决定启动顺序；超过等待窗口后，响应更快的备用源可以先返回，源内音质降级规则保留。成功校验在 15 秒内可能被复用，期间突然失效的直链要等下一次重新校验才会发现；代理 GET 始终依据当次实际响应处理。

没有数据库迁移，不自动调整音质或播放模式。改动需要重新构建并更新运行中的二进制或容器；本轮未部署或重启线上服务。音源返回地址、手机与音源之间的网络、文件大小及解码缓冲仍会影响实际开始出声的时间。
