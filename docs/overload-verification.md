# 并发边界与渐进搜索第二轮验收

2026-09-29，继续上一轮工作区改动，按建议完成并发和排队限制、上游超限报错、流式写超时、搜索节点复用及补充压测。未修改生产数据或重启线上服务。

## 并发额度

| 层级 | 执行上限 | 排队上限 | 范围 |
|---|---:|---:|---|
| HTTP 搜索与播放准备 | 16 | 32 | 同一 Catalog，网页、管理搜索、Subsonic 共用 |
| 同一用户 | 4 | 4 | 上述 HTTP 入口，最多排队 2 秒 |
| 共享上游任务 | 32 | 64 | 新的搜索、直链、校验和目录任务；同键等待者共享名额 |
| JS 调用 | 64 | 128 | 全部 SDK 与音源 Worker 共用 |
| 脚本 HTTP | 8 | 32 | 全部 Worker 共用，响应交给 JS 消费后才释放 |

这些为当前代码默认值。排队有界、取消会移除排队任务，达到个人上限的用户不会挡住有空余额度的其他用户。媒体只在准备响应头期间持有入口名额，不把整首音频下载算作准备任务。目录请求受上游任务和 JS 全局限额约束，未将所有 HTTP 接口统一放入用户入口队列。

入口过载返回 HTTP 503 和两秒重试提示；Subsonic 保留 XML/JSON 错误信封及通用错误码。流式响应已经开始后，以平台 `busy` 事件报告过载，成功结果保留。成功的空结果和平台繁忙分开处理。

音源卸载会取消该 Worker 的在途调用和 HTTP 请求，并释放因事件循环停止而无法继续执行的回调所占的全局名额，避免多次卸载后额度逐渐耗尽。

## 其他改动

- HTTP 正文读取上限加一字节进行探测，超限返回 `ERESPONSETOOLARGE`；没有 Content-Length 的分块响应也受约束。
- 流式搜索每次网络写入最多 3 秒，整个响应写入最多 17 秒；每次刷新成功后恢复整体期限，避免 HTTP/2 在等待慢平台期间被较短写入计时器中断。客户端取消会中止写入，写失败后不再发送后续事件。
- 搜歌和歌单内搜索按同一结果数组追加新行，已有行及按钮保持身份。失败、超时、繁忙和最终完成事件只更新状态；歌单草稿变化只更新对应“加入”按钮状态。
- `music.admission` 提供各层执行、排队与容量拒绝计数；`music.urlPersistence` 记录持久缓存 I/O 耗时。指标不含搜索词、用户身份或媒体 URL。

## 测量

全部测试使用临时数据库和受控上游，没有访问真实音乐平台。

| 场景 | 本机结果 |
|---|---|
| 不同关键词、冷缓存、两个合成平台，100 次并行搜索 | 平均摊销 90.8 µs/次；该值为吞吐口径，不是单请求延迟 |
| 已预热的持久直链缓存，100 次读取 | 约 1.79 µs/次 |
| 100 条不同直链冷写入 | 平均持久化 0.054 ms，最大 0.324 ms |
| 一万条收听记录，持续统计与 100 次用户查询并发 | 用户查询 P95 0.038 ms，业务连接等待 0；统计查询平均 47.1 ms |
| 32 个调用者持续六十秒，混合冷搜索与持续超时，测试额度 4 执行/8 排队 | 1,008,512 次查询，成功平台 24,937 次，繁忙 1,964,292 次，超时 27,795 次；上游并发峰值 4，结束后排队 0 |

持续测试每个查询包含两个平台，因此平台计数与查询数不同；上游容量刻意调小，用于验证过载拒绝和清理。期间每秒采样的 Go 堆最高约 3.29 MiB，不是生产进程 RSS、精确峰值或长期泄漏证明。一分钟测试不能替代数天运行观察。

当前测量中，持久化耗时较低，统计没有造成业务连接等待，因此本轮保留同步持久化与实时统计语义，未追加异步落盘或统计缓存。后续若生产指标显示明显 I/O 等待或统计拥塞，再据此改动，继续保留缓存版本与数据一致性保护。
