# 性能与稳定性优化验收

2026-09-28，从会话 `01a0e6e6-9540-7ab2-99d4-1fbfdf6fd036` 继续实施。开发基线为 `bcadaa3`，本次完成代码修改与隔离验收；线上容器部署不在本次验收范围内。

## 行为变化

- 登录会话定期清理，单用户最多 10 个、全局最多 4096 个；改密、删除用户后撤销会话。会话还绑定加密密码摘要，防止改密前已完成鉴权的并发登录重新建立有效旧会话。管理员改密同时撤销已有调试令牌。
- 登录在鉴权前预占同一用户名一分钟内的 10 次额度，成功登录清零；超限返回 HTTP 429 与 60 秒重试提示。限频表最多 4096 个固定长度摘要键，过期后清理。
- 脚本三种解压操作共同使用 64 MiB 输出上限，多个 gzip 成员也受总上限约束。
- 直链内存缓存每次命中仍更新 LRU，持久使用时间每条每分钟最多写一次；重启恢复上次使用时间。缓存代次、候选源版本、绝对过期、删除及落盘故障回退保护保留。
- 搜索按平台共享请求并缓存成功的非空结果，慢平台与失败平台不阻止网页显示成功结果。网页保持已出现的歌曲位置，后来平台追加到末尾，明确显示错误或超时。原数组 API 和 Subsonic 按平台交错合并；Subsonic 多平台搜索共享 5 秒上游等待预算，单平台 15 秒。
- 歌单编辑逻辑拆至 `playlist-tracks.js`，复用已有歌曲行；移动只改变顺序及必要属性，保留焦点、重复项、草稿版本保护和滚动位置。
- 听歌统计使用最多 2 个独立只读连接和事务快照；业务操作保持原有单连接，降低统计对鉴权及写入的等待影响。
- 新增本地健康检查、Docker 健康指令和管理员性能指标接口。

本次没有修改数据库表结构、真实音源、业务配置或生产数据。静态资源嵌入 Go 二进制，重新构建并部署后才能在运行服务中生效。

## 测量结果与限制

本机 Linux/amd64，Intel i5-13600K，Go 默认并行度 20。所有数据来自临时 SQLite、合成 SDK 和本地 WAV，不访问第三方音乐平台。

| 场景 | 结果 |
|---|---|
| 一万条收听记录、持续统计、100 次用户查询，修改前 | 用户查询 P95 34.26 ms；业务连接累计等待 3343 ms |
| 同场景，独立只读连接后 | P95 0.019–0.025 ms；业务连接累计等待 0 ms |
| 100 次并发重复聚合搜索，5 个合成平台 | 实际上游调用共 5 次；平均摊销约 15.8 µs/次 |
| 开启 SQLite 持久化，100 次已预热直链命中 | 平均约 1.29 µs/次，176 B/次，4 次分配/次 |
| Chromium 中 2000 行歌单下移一次 | 约 9.4 ms；原节点全部复用，焦点与滚动位置保留 |

数值仅用于当前环境的回归基线。并发搜索的摊销时间是吞吐口径，不是单请求 P95；热门直链测量不包含音源请求或媒体下载。一次 DOM 编辑不是浏览器帧率压测。真实上游延迟、网络、生产数据规模及长期峰值内存仍应上线后单独观察，不据此推算整体性能提升倍数。

复现三个后端场景：

```bash
go test ./internal/music ./internal/db -run '^$' \
  -bench 'Benchmark(ConcurrentSearch|PersistentURLCacheHit|ListeningWithUserLookups)$' \
  -benchtime=100x -count=1
```

## 性能接口口径

`GET /api/admin/performance` 使用管理员网页登录 Cookie，普通用户返回 403，未登录返回 401。接口不执行大表查询。

- `database.business`、`database.statistics` 为 Go `sql.DBStats`：`WaitCount` 是累计等待次数，`WaitDuration` 在 JSON 中为纳秒，`InUse`/`Idle`/`OpenConnections` 为瞬时连接数。
- `listening` 是统计查询耗时；`music.search` 按平台统计，包含缓存命中、共享等待和取消。
- `music.urlResolve` 是直链解析；`music.mediaPreparation` 包含解析、响应头校验与换源恢复，不包含媒体正文下载。
- `music.urlCache`、`music.searchCache` 包含 `hits`、`misses`、`shared`、`entries` 和 `inFlight`；命中率按 `hits / (hits + misses)` 计算，`shared` 是未命中请求中加入已有请求的数量。
- `music.sdk.calls.active` 包含正在执行和等待 JS 工作循环的调用；不能将它直接视为 CPU 使用率。
- 操作统计的 `count`/`failed` 为累计完成/失败数，`active` 为在途数，`averageMs`/`maxMs` 为毫秒。`buckets` 是各时延区间的独立计数，`upperMs=-1` 为超过 30 秒的溢出桶，可估计 P95 所在区间，不能提供精确分位数。
- `heapBytes`、`sysBytes`、`goroutines` 是读取时的内存与协程快照；需要持续采样才能观察峰值。

计数仅在当前进程生命周期内累积，重启后清零，不记录用户名、搜索词、播放地址或凭据。

## 健康检查

`GET /healthz` 只返回本地就绪状态，成功为 `{"status":"ok"}`，失败为 HTTP 503；不检查第三方平台可用性。`lxsc -healthcheck` 读取同样的启动配置，访问本机监听地址，以退出码反馈，不启动另一份服务、打开数据库或执行备份恢复。

Docker 镜像每 30 秒检查一次，超时 5 秒，启动宽限 120 秒，连续失败 3 次后标记为不健康。普通 Docker Compose 不会仅因不健康标记自动重启容器；是否重启由部署环境决定。
