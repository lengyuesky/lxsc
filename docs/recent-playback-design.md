# 最近播放日志、飞牛听歌统计与音源调度恢复

2026-11-12，用户确认第一轮 Q1–Q7 与第二轮 Q8–Q13 的全部建议。设计已确认，按以下决定实现。

## 已确认

| 编号 | 决定 |
| --- | --- |
| Q1 | 最近播放日志记录用户的一次播放尝试及交付结果，包含成功与失败，显示实际采用的 302 或代理方式。发出 302 仅代表服务端交付直链，不能认定用户听完整首歌。收听时长另按统计口径计算。 |
| Q2 | “音源”指洛雪音源脚本，“音乐平台”单列。记录实际采用的音源脚本与音频平台，跨平台兜底时保留实际来源。 |
| Q3 | 在现有“听歌统计”页的汇总卡片下方增加“最近播放”。桌面采用列表，手机采用卡片，展示时间、歌曲与歌手、用户、音源、客户端、交付方式和结果。 |
| Q4 | 普通用户仅查看本人记录；管理员可以查看全站并按用户筛选，沿用现有统计权限。 |
| Q5 | 飞牛播放计入“客户端估算”，与“网页实听时长”分别展示。估算方法及去重规则按 Q8–Q9 执行。 |
| Q6 | 持久化现有自动调度所需的音源健康数据，让重启后的调度继续利用已有经验；本次不新增管理员手动排列音源的能力。 |
| Q7 | 最近播放日志持久化到数据库，默认保留最近 30 天；清理最近日志不影响累计听歌统计。 |

## 实施前查证的约束

以下为设计确认时的原实现现状，新增实现见后文。

- 飞牛事件入口当前只解析事件类型和曲目 GUID，只处理 `track_play` 并更新正在播放。当前代码与已归档协议证据不能证明客户端完全不发送其他字段或事件，也没有已核验的暂停、进度、完成事件可用于本次准确计时。见 `internal/fnmusic/media.go`。
- 飞牛登录会话可以关联同一会话的事件与媒体请求，但客户端事件目前没有已核验的唯一 ID 或原始时间戳。秒内重播与重复开始事件无法严格区分；服务端重启后的重新登录也不能严格关联原播放。见 `internal/fnmusic/auth.go`。
- Subsonic 现有客户端估算按正式 scrobble 和歌曲时长计入；缺失时长仅计次数。有原始时间戳时按用户、客户端、歌曲和时间戳去重，无时间戳时每次正式提交都会计数。见 `internal/db/listening.go`。
- 网页实听的 UUID 在每次加载时创建，包括自动恢复，因此不能直接作为一次用户选歌的播放尝试 ID。媒体 URL 目前也没有携带该 UUID。见 `internal/assets/web/listening-tracker.js`、`internal/assets/web/player.js` 和 `internal/assets/web/music-ui.js`。
- HEAD 与独立下载路由可以明确区分；普通 GET 和 Range 请求不能单独证明播放、预取、拖动或实际收听时长。302 仅能确认服务端交付了重定向，代理结束也仅能确认服务端传输结果。见 `internal/mediastream/stream.go` 与 `docs/fnmusic-compatibility.md`。
- 取链结果已有脚本 ID、脚本名及音质，但没有公开的最终平台或最终曲目字段。跨平台兜底的胜出候选需要把来源随结果传递；脚本内部自行换平台时，现有契约无法证明最终上游平台。见 `internal/js/source.go`、`internal/music/url_cache.go` 和 `internal/mediastream/recovery.go`。
- 自动排序使用独立的音源调度样本，每个音源、平台和动作最多 20 个样本，样本有效期 10 分钟；音源页诊断统计是另一份数据。当前样本、连续失败、冷却及限流等待状态均在内存中，连续失败次数目前不随样本过期而清空。见 `internal/js/source_schedule.go`。
- 原始 `history`、累计听歌统计与本次的播放交付日志有不同用途。现有最近歌曲按歌曲分组，原始历史清理只允许 90–3650 天，不适合作为本次每次播放尝试及 30 天清理的口径。见 `internal/db/db.go`、`internal/db/playback.go`、`internal/db/listening.go`。
- 完整备份使用整库 SQLite 快照，已写入数据库的新日志和调度状态会自然进入备份；恢复时仍按当前时间判断调度数据有效期。当前工作树的飞牛功能变更已经使用迁移版本 8，本次后续迁移需顺延；备份清单的 `schemaVersion` 与数据库迁移版本不是同一计数，不能混用。见 `internal/backup/archive.go` 和 `internal/db/migrations.go`。

## 第二轮已确认

| 编号 | 决定 |
| --- | --- |
| Q8 | 飞牛每个去重后接受的 `track_play` 计一次客户端估算，并按已知歌曲总时长累加；缺失时长仅计次数。快速切歌或立即暂停可能高估，页面明确说明。 |
| Q9 | 飞牛按用户、服务端登录会话和歌曲，在首次接受事件后的固定 5 秒内合并重复 `track_play`，不滑动延长窗口；期间播放过另一首歌或超过窗口再播，计为新播放。缺少可靠事件 ID 时，秒内真实重播可能被合并，迟到重试也可能重复计数。 |
| Q10 | 有可靠播放标识时，一次选歌或开始事件对应一条主记录，自动重试和 Range 请求放入该条详情。缺少标识、无法区分播放和预取时，明确标为“媒体请求”，不宣称每条对应一次真实收听；HEAD 和独立下载不作为收听记录。 |
| Q11 | 主列表展示最终采用的脚本、服务端最终选中的取链平台、音质、交付方式与结果；展开查看失败音源、降档、跨平台兜底、缓存命中及传输中断。脚本内部的最终上游无法验证时明确标注可观测范围，不把原曲目平台当作已验证的最终来源。 |
| Q12 | 默认按时间倒序显示 50 条并支持加载更多，沿用用户范围筛选，增加歌曲关键词、音源、客户端、交付方式和结果筛选。仅页面可见时每 30 秒刷新；查看旧记录或操作筛选时保留当前阅读位置。 |
| Q13 | 调度恢复保留原 10 分钟样本有效期，停机时间计入过期，冷却与限流按原截止时间恢复；较长停机后重新积累排序样本。连续 10 分钟没有新调度样本时清空陈旧的连续失败惩罚。相同脚本内容的停用和启用保留健康经验，脚本内容变化重新学习该源并重置对应失败、冷却和限流状态，删除音源清理对应状态；运行中的调用与探测锁在重启后释放。 |

## 新增实现

- 数据库迁移 9 新增播放主记录、请求明细和音源调度状态。用户、歌曲、脚本名称使用日志快照，删除音源后既有播放记录仍可查；删除用户按现有级联规则清理其日志。分页使用时间与编号游标，不受并发新增日志扰乱。
- 共享媒体层记录准备、取链、失败音源、缓存校验、跨平台兜底与交付结果。最终平台和曲目从胜出候选随解析结果传递；源内不可观测的上游平台不作已验证来源展示。长代理传输在准备后即可查看音源与明细，结束时更新完成／中断结果。
- 网页每次主动选歌、重播或循环创建独立播放标识，自动降质沿用该标识，多个 Range 请求累加在同一条详情中。该标识与网页实听上报的会话分别管理，不携带凭据。
- 飞牛登录会话另设独立随机关联 ID。接受的 `track_play` 在同一事务内更新日志归类、客户端估算和旧播放历史；固定 5 秒去重窗不被重复事件延长。开始事件前的近期媒体请求可以随后关联；同曲较晚的完整取流先独立记录，避免重播先取流后上报时永久合并到旧播放。不能确认归属的请求保留“媒体请求”标记。
- 最近日志每小时分批清理 30 天前的记录，查询也受留存范围限制；保留最新 100 条请求明细及明细总数量。启动时将上一个进程没有保存结束结果的“准备／传输中”日志改为“结束结果未确认”，不会据此补算收听。
- 调度状态按音源 ID 和脚本内容指纹保存原始样本，后台合并写入、失败重试；启动前恢复，退出及完整备份前补写。脚本变更重置旧调度状态，旧脚本的迟到取链与媒体反馈不能污染新脚本。缓存命中仍遵守原取链缓存契约，持久化排序经验不强制清缓存。
- 普通用户／管理员的列表、详情和筛选选项全部经过同一归属校验；不记录媒体地址、请求头、票据、票据摘要或设备密钥。前端换号取消旧请求，加载更多与详情操作独立于累计统计的日期控件。
