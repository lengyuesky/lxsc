# 音频内容验证

播放候选成功的标准改为：服务端实际读取有界的音频片段，并由 FFmpeg 成功解码出 PCM 样本。HTTP 200/206、`audio/*` 响应头或文件签名本身都不能使候选胜出。

每个候选最多读取 256 KiB，解码使用一次播放准备的既有期限，并且全进程最多同时运行四个解码任务。解码器只接收内存中的片段，不能自行打开额外文件或网络地址。空正文、错误内容、无法解码的数据或缺少 FFmpeg 均不会被包装成验证成功。服务端验证起始音频片段，不预先下载整首歌曲；这不能证明整首文件后续没有损坏，也不替代客户端网络与格式兼容性。

取链成功统计继续表示音源返回了地址。只有内容验证通过的候选才发布为已验证播放链接、增加媒体成功评分并结束竞速。内容失败允许同一脚本继续尝试较低音质；网络、限流和源认证仍受原有预算与退避限制。所有合格脚本继续进入候选集合，受并发、期限及最多 24 次尝试约束，不保证每次请求都能耗尽所有脚本与音质组合。

## 直链与代理

保持管理员原有交付方式。QQ 和 HTTP 直链在直链模式中仍返回 302，不会自动改成本站代理，也不改写地址或签名。服务端读取的片段仅用于验证，不作为直链音频正文转发给客户端。

管理员明确选择代理时，已经消费的验证片段会完整放回响应流，避免丢失音频开头。非零 Range 请求独立验证原文件起始片段，然后检查所请求片段可读，保留 Range/If-Range 与 Content-Range。正文交付开始后发生错误不会重播整首歌曲；上游读取失败会撤销该版本的验证缓存并记录失败反馈。

解码器确认的媒体类型用于本站 HEAD 元数据及显式代理响应。302 后客户端直接访问上游，本站不会修改上游音频的响应头。

网页在尚未开始播放时最多自动尝试两个较低音质；切歌、暂停、退出或旧请求回调不会继续恢复，已经播放的音频发生后续错误也不会重播整首歌曲。

## 私有诊断

已有 `/api/debug/probe`、`/api/debug/probe/protocol` 和 `/api/debug/probe/playback` 保持原有只读取响应头的契约。媒体预检标记 `validation=headers_only`，不表示音频可播放，也不会为媒体增加成功评分。只取头的缓存与实际解码验证缓存隔离。

新增 `POST /api/debug/probe/audio`，要求 `probe + inspect`，请求示例：

```json
{"trackId":"tr-wy-123456","quality":"320k"}
```

该接口使用实际音频内容验证。结果 `validation=validated` 表示服务端解码通过，失败返回固定错误类别，例如 `invalid_audio`、`decoder_unavailable`。接口可以更新验证缓存和音源评分，但不返回音频正文、不记录播放或收听统计。由于换源可能多次读取片段，256 KiB 是每次候选的上限，不是整次探测的总流量上限。必须先读取 capabilities，再按实际权限选择接口；诊断数据仅供管理员授权的受信任排查者使用。

## 运行与验证

Docker 镜像包含 FFmpeg；直接运行二进制时，`ffmpeg` 必须位于 PATH。缺少解码器时应安装依赖，不能退回仅检查响应头的假成功。

隔离测试使用自主生成的 440 Hz PCM、MP3、FLAC，不使用真实歌曲、线上账号或音源。覆盖假音频、空正文、伪造签名、真实解码、错误 MIME、验证前缀完整交付、同源降档、不同源恢复、只取头权限隔离、私有音频探测，以及 QQ/HTTP 继续直链。
